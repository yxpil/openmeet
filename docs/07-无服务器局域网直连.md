# 无服务器局域网直连（设计与验证状态）

> 状态：**已完整实现并端到端验证**（协议内核 + 主进程 IPC + 渲染层传输适配器 + 双客户端真机验证）。
> 同机双客户端可验证发现、建链、媒体与聊天；多网卡与组播被交换机过滤的环境仍需两台机器验证。

## 1. 目标与边界

现有"局域网会议"仍要求**主机进程在线并跑内嵌服务**：主机离开，会议就散。
本模式要的是同一网段内**没有任何协调者**的会议——每台客户端自己发现彼此、
自己承载信令、直接建立 WebRTC mesh。

明确不做：跨互联网无服务器开会。没有 STUN 拿不到公网地址，没有 TURN 打不通对称 NAT；
那属于另一类取舍（第三方信令或自建服务），不在此模式内。

## 2. 房间身份：口令不出本机

```
roomId = HMAC-SHA256(key = passphrase, msg = "om-p2p-v1:" + 规范化(code)).hex[0..32]
```

- 广播里只出现 `roomId`，不出现口令，也不出现明文房间号；旁听者既进不来，也认不出这是哪场会。
- 加入者必须能算出同样的 `roomId` 才能通过 `hello` 校验 → 口令即准入。
- 会议号由房内成员自行约定：`^[A-Z0-9]{4,16}$`，规范化时去掉分隔符并转大写。
  **不复用服务器的 9 位房间码规则**（`normalizeRoomCode` 会强制 `ROOM_CODE_PATTERN`，
  用它校验自定义会议号会把合法输入判成非法）；统一使用 `normalizeP2pCode()`。

**已知弱点（v1 有意接受，需在 UI 与文档中说明）**：`roomId` 是**持有即生效**的凭据，
拿到它的人可以伪造广播。它等价于"房间口令"，但不含时效与成员签名，
因此不防重放——局域网内信任模型下可接受，跨信任域请改用服务器会议。

## 3. 发现与建链

| 环节 | 做法 |
| --- | --- |
| 发现端口 | 所有节点在**同一个 UDP 端口** `45872` 上监听（`reuseAddr`）。信令端口是临时的、每台机器不同，因此** beacon 的 `port` 字段携带自己的信令端口**，收到后按该端口拨号。把 beacon 发到自己信令端口的写法曾导致真实网络下永远发现不了彼此 |
| 宣告 | 每 2 秒向 `255.255.255.255`、本机子网定向广播、`239.255.45.87` 组播发 UDP beacon；组播不可用时自动退化为广播 |
| 内容 | `{m:'om-p2p', v, room, peerId, name, host, port, kind, sentAt}` |
| 建链方向 | **peerId 较小的一方主动连**，保证全图只有一条 TCP 连接，不会双向重复 |
| 鉴权 | 首帧必须是 `hello` 且 `room` 与本机推导一致，否则以 `4001 room mismatch` 关闭 |
| 名册扩散 | `welcome` 携带现有成员 + `referral` 转发，新成员一次拿齐全图，mesh 自动闭合 |
| 离开 | 关闭时发 `bye`（UDP）与 `leave`（WS）；只发 `bye` 失败也没关系 |
| 掉线 | 7 秒未见任何 beacon/链路活动即从名册剔除并通知（模拟机器直接断电） |

链路消息类型：`hello / welcome / referral / signal / media / chat / hand / mute-request / leave`。

## 4. 与现有会议逻辑的关系

`MeetingClient` 与协调者的全部耦合只有三处：连接+握手、`send(ClientMessage)`、
`onmessage(ServerMessage)`。因此本模式**不重写 mesh**，而是把这三处抽成
`MeetingTransport`（`bind / start / send / close`），由适配器实现：

```
LanP2pTransport  ──把 P2P 事件合成为──▶  ServerMessage 形状（welcome / peer.join /
                                          peer.leave / peer.update / signal / chat）
                                        ▼
                              现有 MeetingClient 与渲染层不变
```

约定：

- 未提供 `transport` 时 `MeetingClient` 走原来的 WebSocket 分支，一行未改，
  服务器会议的既有验证继续有效。
- 适配器只发一次 `welcome`，之后全部为名册差分（`peer.join/leave/update`），
  避免 `welcome` 触发 `teardownPeers()` 打断已建立的 PeerConnection。
- 自己的聊天消息由适配器本地回显（服务器原先也是这么做的），历史落盘逻辑不变。
- `room.mute` 映射为 `mute-request`；等候室、锁定、踢人、主持人移交等没有强制方的
  动词被忽略，因为 UI 在无服务器模式下不会给出这些入口（所有人都是 `participant`）。
- 无服务器会议没有邀请令牌，邀请弹窗改为提示"用其它渠道交换会议号与口令"。

### 4.1 三个真实踩到的时序坑（都已在验证中复现并修掉）

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| 远端只有头像，收不到画面；一旦对方切换麦克风画面立刻出现 | `MeetingClient` 在 `welcome` 里发出自己的媒体状态，而 `welcome` 是在 `transport.start()` **内部**发出的，此时 `transportOpen` 仍为 false，状态被丢弃 → 对端以为你没有开摄像头，把视频块隐藏了 | 绑定处理器后立即置 `transportOpen = true`，就绪判断交给 transport 自己的 `send()` 返回值 |
| 协商永不完成，双方 `tracks=0` | 服务器会议由服务端保证"先 `peer.join` 后有 `signal`"；mesh 没有这个顺序权威：offer 可能先到、或链路尚未建立就被丢弃 | 适配器遇到未知来源的 `signal` 先合成一次 `peer.join`；节点侧把链路就绪前收到的 `signal` 排队，`socket` 可用后按序冲刷 |
| 名册里新链路对端的媒体状态一直是全关 | beacon 只带名字与地址、不带状态，名册条目由 beacon 建立时状态为空 | 链路可用时（`hello` 之后 / `welcome` 之后）立刻补发一帧 `media`，不等下一次开关变化 |

另外：一台机器只有一个摄像头时，Windows 只把摄像头交给一个进程；第二个客户端会
自动降级为"仅音频"并提示"无法访问摄像头，你仍然可以加入会议"——这条降级路径本身
就是产品要求的行为，端到端脚本因此固定让第二个客户端不开摄像头，以便断言
"画面确实到达并显示"，而不是依赖两个进程抢同一个设备。

## 5. 权限模型的退化（必须写进 UI）

没有协调者就没有强制方：

| 能力 | 服务器会议 | 无服务器直连 |
| --- | --- | --- |
| 准入 | 口令 + 等候室由服务端强制 | 仅口令（`roomId` 校验），**无等候室** |
| 锁定房间 | 服务端拒绝 | 只能拒绝新 `hello`，已进名册者无法追溯 |
| 静音他人 | 服务端下发 `moderation` | `mute-request` 只是**请求**，对端可自行忽略 |
| 移出成员 | 服务端断开其信令 | 无法强制，只能各自断链 |
| 主持者移交 | 服务端记录 | 无权威状态，不做主持者概念 |
| 会议历史/聊天留存 | 本机 SQLite | 同样可存本机，但无服务端备份 |

因此该模式定位是**同信任域内的临时会议**（同一间会议室、同一办公室），
不是对外公开会议的替代品。

## 6. 实现与验证

单元测试（`packages/desktop/test/p2p-node.test.ts`，5 项）：

- `deriveRoomId` 规范化与区分度（口令不同→摘要不同；分隔符无关）
- 双节点发现、单方向建链、`signal` 双向送达、`chat` 送达、`media` 状态扩散
- **口令错误的节点无法加入名册**
- beacon 发到共享发现端口，且携带的是信令端口（守住上面那条不变式）
- 无 bye 消失的对端在超时后被剔除

端到端（`node packages/desktop/scripts/e2e-lan-p2p.mjs`，两个真实 Electron 实例，
**全程不启动任何服务器、不使用账号**，通过 CDP 驱动真实界面）：

- 首页 → 局域网会议 → 无服务器直连 → 填会议号/口令/显示名 → 预览页 → 入会
- 双向发现：`["甲我","乙"]` / `["乙我","甲"]`，显示名取自对话框（曾经被静默丢弃过）
- **画面确实到达并被渲染**：乙关闭摄像头，乙的远端块仍拿到 320×180 的真实帧，
  且断言 `<video>` 未被隐藏（收到轨道却显示头像，是用户可见的缺陷而非"没问题"）
- 甲一侧的轨道为 `muted=true`，正确反映乙没有摄像
- 聊天经 mesh 送达对端，发送方本地回显一次
- **对端离开后会议不终止**，本机仍在会议中且名册更新——这正是无协调者的意义

仍未覆盖：

- 两台物理机器、多网卡选择：当前广播 `host` 取第一个非回环 IPv4，未让用户挑选，
  多网卡机器（如有线 + Wi-Fi + VPN）可能宣告了成员到不了的地址
- 组播被交换机/防火墙过滤的环境只能依赖子网定向广播
- 屏幕共享与举手在无服务器模式下的表现（复用同一套 mesh 代码，未单独验证）
